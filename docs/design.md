# Проект решения: backend-визитка

2026-11-07. Решение принято пользователем. Реализация начата.

## Цель и подход
Backend с публичным GraphQL API чтения и Apollo Sandbox на /graphql. Один профиль со связанными навыками, профессиональными ссылками, опытом и проектами.
Выбор: модульный NestJS с PostgreSQL. Микросервисы избыточны; прямые запросы Prisma из resolver проще, но ухудшают разделение ответственности.

## Архитектура
GraphQL resolver отвечает за API и типы. ProfileService — за сценарий чтения. ProfileRepository — за запросы Prisma. PrismaModule — за жизненный цикл подключения.
Таблицы: Profile, ProfessionalLink, Skill, Experience, Project. Связи через profileId, устойчивые ключи и явная сортировка.
Experience: company, position, startDate, nullable endDate, achievements. Project: name, url. ProfessionalLink: label, url.
Query profile возвращает профиль либо null при отсутствии; после штатного seed профиль существует.
Публичные mutations, авторизация и админка в объём не входят.

## Вложенные данные
Для единственного профиля репозиторий явно загружает связанные коллекции ограниченным числом запросов, независимым от числа записей. Компромисс — возможная избыточная выборка при узком GraphQL-запросе, зато нет сложного разбора AST.
Не обещать один SQL JOIN: проверить фактические запросы Prisma. Интеграционный тест сравнивает количество запросов при разных размерах коллекций. При добавлении списка профилей пересмотреть стратегию и при необходимости добавить пакетную загрузку.

## Инициализация
Docker Compose: PostgreSQL с healthcheck и volume, приложение ждёт готовности БД.
При старте: сохранённые миграции, транзакционный идемпотентный seed, затем сервер. При ошибке инициализации сервер не запускается. Повторный seed не дублирует данные и не сбрасывает всю БД.
Многостадийный Dockerfile, lockfile, .env.example без настоящих секретов. Совместимость конкретных версий проверить по официальной документации до установки.
