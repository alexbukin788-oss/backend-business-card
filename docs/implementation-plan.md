# План реализации backend-визитки

Принят к исполнению 07.11.2026 по поручению владельца; работаем в этом чате без субагентов.
Навык исполнения: superpowers:executing-plans. Спецификация: docs/design.md.

Цель: GraphQL-визитка с автоматической подготовкой PostgreSQL и Apollo Sandbox.
Архитектура: resolver → service → repository → Prisma → PostgreSQL. Отдельный Compose-проект.
Стек: Node24, TypeScript6, Nest12, Prisma7, GraphQL16, Apollo5, PostgreSQL17, Docker, Git.

## Общие ограничения
- Новый независимый Git-репозиторий backend-business-card; не использовать репозитории сказок/открыток/причёсок.
- Никаких изменений существующих серверных приложений, файлов, баз, HTTPS-конфигурации и сети.
- Для проверок создать только собственные ресурсы с префиксом backend-business-card, БД доступна только локально на сервере.
- Только явно обозначенные демонстрационные данные. Реальные данные нужны перед сдачей.
- Публичный адрес и назначение GitHub подтвердить перед публикацией конкретного результата.
- Не использовать RC-версии: latest Prisma сейчас RC8, выбираем совместимые стабильные CLI/client/adapter7.10.1; TS6 соответствует peer dependencies NestGraphQL.

## Этап 1 — основа и данные (1.5–2.5 часа)
Файлы: package.json, tsconfig.json, prisma.config.ts, prisma/schema.prisma, prisma/migrations/, prisma/seed.ts, src/database/client.ts, src/profile/profile-data.ts, src/profile/seed-profile.ts, test/unit/profile-data.test.ts, test/integration/seed.test.ts.
Интерфейсы: ProfileData — имя/описание/ссылки/навыки/опыт/проекты; validateProfileData(data):void; seedProfile(client,data):Promise<void>.
- [x] Независимый Git, фиксированные версии зависимостей и lockfile.
- [x] Тесты сначала: пустое имя, неверные URL/периоды; валидный демонстрационный профиль принимается.
- [x] Реализовать типы и проверку наполнения, реляционную схему с каскадными связями и индексами profileId/position.
- [x] Миграция и транзакционный seed одного профиля: повторение без дубликатов, обновление и удаление устаревших дочерних записей только своего профиля.
- [x] На отдельной PostgreSQL доказать чистую миграцию, повторный seed и откат при ошибке. Результат: база воспроизводимо готовится.

Файлы: src/main.ts, src/app.module.ts, src/database/database.module.ts, src/profile/{profile.module,profile.repository,profile.service,profile.resolver,profile.model}.ts, test/integration/api.test.ts.
Интерфейсы: repository.findProfile(profileId:string):Promise<ProfileRecord|null>; service.getProfile():Promise<ProfileRecord|null>; query profile:Profile.
- [x] Тесты запроса работодателя, всех полей, сортировки и отсутствующего профиля.
- [x] Реализовать слои и code-first схему с датами и достижениями, health/readiness.

Результат: запрос работодателя возвращает профиль со связями, Sandbox доступен.

- [x] Многостадийная сборка, непривилегированный runtime, лимиты памяти/CPU/логов, свой volume/network, никаких общих БД.
- [x] При старте migrate deploy → seed → node; ошибка инициализации прекращает запуск.
- [x] Поднять с чистой собственной БД, выполнить запрос из задания, повторить запуск без дубликатов.
- [x] Проверить unit/integration, health/Sandbox, graceful shutdown и отсутствие публичного порта БД.
Результат: проверенный Docker-запуск с нуля без ручной подготовки базы.

## Проверки краевых случаев
Пустые коллекции и отсутствие профиля (этап2); обновление/повторение seed (этап1); ошибочные данные и атомарность (этап1); рост вложенных данных без N+1 (этап2); недоступная БД и повторный Docker-старт (этап3).

Оценка оставшейся работы:7–12часов без ожидания доступов/личных данных. Сначала закрываются локальные и изолированные проверки; публикация не считается выполненной до проверки реальных ссылок.
