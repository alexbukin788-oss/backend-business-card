# Backend-визитка

TypeScript / Node.js / NestJS / Prisma / PostgreSQL / GraphQL / Docker.
API показывает профиль, профессиональные ссылки, навыки, опыт с датами и достижениями, проекты. Apollo Sandbox доступен на `/graphql`.

Временная демонстрация: https://olympics-socket-undo-sociology.trycloudflare.com/graphql
Адрес проверен 07.11.2026; может измениться после перезапуска туннеля. Инструкция — `docs/operations.md`.

Профиль Алексея Бурого заполнен по резюме HeadHunter и подтверждённым проектам. Источник данных — `prisma/profile.data.ts`. Опыт указан как самостоятельная разработка собственной платформы с помощью Codex. Начальная дата 02.10.2026 — самая ранняя найденная запись о принятии ТЗ и реализации платформы, а не подтверждение даты возникновения идеи. Телефон, личная почта, возраст и зарплатные ожидания не публикуются.

## Запуск с нуля

Нужны Git, Docker Engine/Desktop и Docker Compose v2 или новее. Локальная установка PostgreSQL и Node.js для Docker-запуска не требуется.

```sh
git clone https://github.com/alexbukin788-oss/backend-business-card.git
cd backend-business-card
cp .env.example .env
# В .env заменить POSTGRES_PASSWORD длинным случайным значением из букв/цифр.
docker compose up --build -d --wait
```

В Windows PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`.
Открыть `http://localhost:4310/graphql`. Корень сайта перенаправляет на Sandbox. Проверка готовности: `http://localhost:4310/health`.

Compose автоматически запускает собственную PostgreSQL, ждёт её готовности, применяет миграции и заполняет профиль. Только после успешной инициализации запускается API. При ошибке база/инициализация не выдаются за готовое приложение. Повторный запуск не создаёт копии записей.

Порт приложения привязан к `127.0.0.1`. Это намеренно: для публичной демонстрации требуется отдельный HTTPS-адрес и проксирование к этому порту. База не публикует порт в основном Compose-файле.

## Запрос работодателя

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Полный запрос:

```graphql
query BusinessCard {
  profile {
    name
    description
    links {
      label
      url
    }
    skills {
      name
    }
    experience {
      company
      position
      startDate
      endDate
      achievements
    }
    projects {
      name
      url
    }
  }
}
```

Даты хранятся как PostgreSQL `DATE` и выдаются как ISO-время в UTC (полночь). `endDate: null` означает работу по настоящее время. Коллекции возвращаются в порядке исходного файла данных. Если профиль отсутствует, ответ — `profile: null`; пустые коллекции — `[]`. API предназначен для чтения; mutations отсутствуют.

## Почему такая архитектура

- `profile.resolver.ts` описывает точку входа GraphQL, без SQL и наполнения базы.
- `profile.service.ts` представляет сценарий получения визитки. Сейчас логика короткая: дополнительных бизнес-правил в задании нет. Это точка для будущих правил, без искусственных абстракций.
- `profile.repository.ts` выполняет запросы через Prisma; GraphQL не управляет SQL.
- `database/` отвечает за подключение, пул (максимум 5 соединений) и корректное закрытие.
- `prisma/` содержит схему, сохранённую миграцию и редактируемые данные.

Один профиль и четыре связанные таблицы вместо JSON-поля: явные типы, внешние ключи, индексы и предсказуемая сортировка. Редактирование профиля через административный API не требуется, поэтому оно не добавлено. Микросервисы, CQRS и универсальный репозиторий для этой задачи избыточны.

### Вложенные данные и N+1

Репозиторий сразу получает профиль и четыре коллекции. Нет resolver, который обращается к БД для каждого навыка или проекта. В используемой конфигурации Prisma это ограниченная пакетная выборка (до 5 SELECT), а не обещание единственного SQL JOIN. Интеграционный тест измеряет реальные SQL-запросы и проверяет, что увеличение коллекции не увеличивает их число.

Компромисс: даже запрос только имени загружает остальные небольшие коллекции. Для единственной визитки это проще и понятнее разбора GraphQL AST. При добавлении списка профилей или больших коллекций нужно пересмотреть выборку, добавить пагинацию и при необходимости DataLoader. Не выдаём это решение за универсальный API большого каталога.

### Миграции и повторное заполнение

`prisma migrate deploy` применяет сохранённые SQL-миграции, а не меняет схему через `db push`. Seed проверяет данные, берёт транзакционную блокировку на инициализацию профиля и обновляет профиль вместе с коллекциями в одной транзакции. Его повторение не добавляет дубликаты, удалённые из исходного файла элементы исчезают. При ошибке записи транзакция откатывается. Другие профили не удаляются.

Источник истины — `prisma/profile.data.ts`: ручные изменения именно этого профиля в БД будут заменены при следующем запуске. Внутренние числовые ID дочерних строк могут изменяться при seed и не являются публичными идентификаторами API.

## Разработка и проверки

Node.js 24 (>=24.11), pnpm 11.25.0. Версии зависимостей зафиксированы в manifest/lockfile. NestJS 12 использует ESM; TypeScript и Prisma настроены согласованно.

```sh
pnpm install --frozen-lockfile
pnpm generate
pnpm build
pnpm test
```

Для интеграционных тестов используется **только отдельная тестовая база**:

```sh
docker compose -f compose.test.yaml up -d --wait
# DATABASE_URL в .env: postgresql://business_card:<пароль>@localhost:55439/business_card_test
pnpm migrate
pnpm test:integration
```

Тестовый Compose публикует PostgreSQL исключительно на `127.0.0.1:55439`. Если используете SSH-туннель, укажите локальный порт туннеля (например, 15439) в DATABASE_URL. Тесты намеренно меняют/удаляют записи и отказываются работать, если имя базы не `business_card_test`. Не направляйте их на рабочую БД.

Проверяются: валидация, чистая миграция, повторный seed, обновление коллекций, сохранение постороннего профиля, реальный откат при ошибке PostgreSQL, запрос работодателя, полная схема, пустые данные, отсутствие профиля, ограниченное число SQL, HTML Sandbox, readiness и отсутствие mutations.

Запуск приложения без Docker после миграций:

```sh
pnpm seed
pnpm start
# http://localhost:3000/graphql
```

`DATABASE_URL` при этом должен указывать на вашу базу. Для изменения схемы в разработке создавайте новую миграцию; опубликованные миграции не редактируйте.

## Операции и ограничения

- `docker compose logs --tail=100 app` — журнал только этого приложения.
- `docker compose down` — остановить и убрать контейнеры/сеть визитки; данные сохраняются.
- `docker compose down --volumes` — **необратимо удалить также данные визитки**; выполнять только осознанно из её каталога после проверки имени проекта.
- Не применять общесерверные `docker system prune` или команды удаления всех контейнеров.
- После изменения данных: `docker compose up --build -d --wait`.
- Постоянные данные лежат в собственном volume; остальные проекты его не используют.
- Runtime работает не от root, без Linux capabilities, с лимитами CPU/RAM и ротацией журналов. Это разделение приложений, не отдельная виртуальная машина: ресурсы сервера общие.
- В runtime включён Prisma CLI для миграций при запуске. Это увеличивает образ, но делает запуск одной командой воспроизводимым; отдельный migrator здесь усложнил бы передачу задания.
- Sandbox и introspection включены намеренно для демонстрации. Его интерфейс загружается с сервисов Apollo, поэтому браузеру нужен доступ к ним.
- Исходники: https://github.com/alexbukin788-oss/backend-business-card. Публичный адрес приложения и реальные данные пока не настроены. Это не готовая к отправке работодателю публичная версия.

Подробнее о развёртывании и границах изменений — `docs/operations.md`.
